# AWS S3 — Complete Notes + Interview Questions

---

## What Is S3? Full Form and the Big Picture

**S3 = Simple Storage Service**

The name tells you exactly what AWS was going for — a storage service that is *simple*. And compared to every other AWS service, it genuinely is. No servers to launch, no OS to configure, no networking to set up. You create a bucket, you upload a file, and that file is instantly accessible from anywhere in the world via a URL. That's it.

S3 is an **object storage service**. This is an important distinction:

| Storage Type | What It Is | Examples |
|---|---|---|
| **Block Storage** | Raw storage divided into blocks, attached to a single server like a hard drive | EBS (EC2's disk), your laptop's SSD |
| **File Storage** | Hierarchical folders and files, shared across multiple servers | EFS (AWS), NFS, Windows File Share |
| **Object Storage** | Flat storage — each "object" is a file + its metadata + a unique key (URL) | S3, Google Cloud Storage |

In object storage, there are no folders in the traditional sense. Everything is a flat list of objects identified by a key (essentially a path). `photos/2024/trip.jpg` looks like a folder structure, but S3 sees it as a single object with the key `photos/2024/trip.jpg`. The `/` is just part of the name, not a real directory.

---

## Why Is S3 the Easiest AWS Service?

Here's why every AWS beginner starts with S3:

**1. Nothing to provision.** With EC2, you choose an instance type, configure storage, set networking, select an OS. With S3, you click "Create Bucket," give it a name, and it exists. Done.

**2. Nothing to maintain.** No OS to patch. No disk to monitor. No capacity planning. AWS manages all the underlying hardware, redundancy, and scaling invisibly.

**3. Immediate access via a URL.** Every object in S3 has a unique HTTPS URL. If the object is public, anyone can access it by pasting the URL in a browser. No server, no application needed.

**4. No storage limit to worry about.** You don't say "I'll need 500GB." You just upload and S3 holds whatever you put in it.

**5. Pay as you go.** No upfront commitment. If you store 1GB for one month, you pay for 1GB for one month.

## What Can S3 Store?

S3 can store **any type of file** — there are no restrictions on file format. Anything that can be represented as bytes can be stored.

**Everyday files:**
- Images (JPG, PNG, GIF, SVG)
- Videos (MP4, MKV, AVI) — yes, full movies
- Audio files (MP3, WAV, FLAC)
- Documents (PDF, DOCX, XLSX)
- Text files, CSVs, JSONs, XML

**Code and web files:**
- HTML, CSS, JavaScript files
- Python, Node.js, Java application packages
- Docker images (though ECR is preferred)
- ZIP files, TAR archives

**Data and analytics:**
- Database backups and dumps (SQL files)
- Log files from servers and applications
- CSV/Parquet/ORC files for data lakes
- Machine learning training datasets (terabytes)

**Infrastructure and DevOps:**
- Terraform state files
- CloudFormation templates
- CI/CD deployment artifacts
- AMI snapshots (indirectly — EBS snapshots are backed by S3)

**One object can be up to 5TB in size.** For objects over 5GB, you must use multipart upload. For objects over 100MB, multipart upload is recommended for performance.

## What Do Organizations Use S3 For?

**1. Backup and Disaster Recovery**
Every database, every server, every important file gets backed up to S3. It's cheap, durable, and accessible from anywhere. RDS can automatically export backups to S3. EC2 snapshots can be stored there.

**2. Data Lake**
Large companies dump ALL their raw data — logs, transaction records, user events, sensor data — into S3 in its original format. This becomes a "data lake." Tools like Amazon Athena can then query this data directly using SQL without loading it into a database.

**3. Content Delivery (with CloudFront)**
Images, videos, and static assets for websites are stored in S3. CloudFront (AWS's CDN) sits in front and serves them from edge locations near users globally. Netflix-style video streaming uses this pattern.

**4. Static Website Hosting**
HTML, CSS, and JavaScript-only websites can be hosted directly from S3 — no server needed. React and Angular SPAs (Single Page Applications) are commonly hosted this way.

**5. Software Distribution**
Companies distribute software packages, updates, and installers through S3. Users download from an S3 URL. AWS itself distributes its CLI and SDKs this way.

**6. Log Archival**
CloudTrail logs (AWS API activity), VPC Flow Logs, ALB access logs, and application logs are all sent to S3 for long-term storage and compliance audits.

**7. Machine Learning**
Training datasets for ML models (which can be hundreds of gigabytes) live in S3. SageMaker (AWS ML service) reads training data directly from S3.

## S3 Is a Globally Accessible Service — Explained

This is slightly nuanced. Here's the accurate picture:

S3 **buckets** are created in a specific AWS Region (Mumbai, US-East, etc.). The data physically lives in that region. So technically, S3 is a **regional service** from a data residency perspective.

But S3 **endpoints** (the URLs you use to access objects) are accessible from **anywhere in the world** over the public internet, as long as you have the URL and permission.

**This is what "globally accessible" means:**
- A user in India, the US, and Australia can all access the same S3 object URL simultaneously
- No VPN needed
- No specific regional configuration on the client side
- Just an HTTPS URL that works from any browser or application anywhere

**S3 Bucket URL format:**
```
https://bucket-name.s3.region.amazonaws.com/object-key
```

Example:
```
https://my-company-assets.s3.ap-south-1.amazonaws.com/images/logo.png
```

Anyone, anywhere in the world, can paste this in a browser and access it (if it's public).

## HTTPS and S3 — Why It Matters

Every S3 URL uses **HTTPS** — Hypertext Transfer Protocol Secure.

**What HTTPS does:**
- **Encrypts** the data in transit between the user and S3 — nobody can intercept and read the file as it travels over the internet
- **Authenticates** the server — your browser verifies it's actually talking to AWS and not an impersonator (via SSL certificate)
- **Ensures integrity** — the data you receive hasn't been tampered with in transit

**Why this matters for S3:**
When you download a file from S3 (say a backup or a document), HTTPS ensures:
- The file wasn't read by anyone in the middle
- The file wasn't modified in transit
- You're talking to the real AWS S3, not a fake server

AWS enforces HTTPS-only for S3 by default. You can add a bucket policy condition to explicitly deny any HTTP (unencrypted) requests.

S3 also encrypts data **at rest** — while it's stored on AWS's servers — which is a separate layer from HTTPS (which is encryption **in transit**).

## What Does 11 9s Reliability Mean?

S3's durability rating is **99.999999999%** — that's eleven 9s. This is one of the most impressive reliability claims in cloud infrastructure.

Let's understand what this means practically:

**11 nines written out:** 99.999999999%

The remaining failure rate is: 0.000000001% — or 1 in 100 billion.

**What this means in real terms:**
If you store **10 million objects** in S3, you would expect to lose **one object** approximately every **10,000 years**.

You're statistically more likely to be struck by lightning than to lose a file stored in S3 due to S3's fault.

**How AWS achieves 11 9s:**
S3 automatically stores **multiple copies** of every object across **at least 3 physically separate Availability Zones** within the region. If a disk fails, a server fails, or even an entire data center burns down — your data still exists on the other copies. AWS continuously monitors and repairs data silently in the background.

**Important distinction — Durability vs Availability:**

| Term | What It Means | S3 Value |
|---|---|---|
| **Durability** | Will the data still EXIST? (won't be lost/corrupted) | 99.999999999% (11 nines) |
| **Availability** | Can you ACCESS the data right now? | 99.99% (Standard class) |

Durability is about the data surviving. Availability is about whether the S3 service is up and responding. S3 Standard has 99.99% availability — meaning S3 could be inaccessible for a maximum of about 52 minutes per year and still meet its SLA.

## Storage Capacity of S3

**There is no maximum storage limit for S3.** 

- **Total bucket storage:** Unlimited
- **Number of objects per bucket:** Unlimited
- **Number of buckets per account:** Default limit of 100 (can be increased to 1000 via service quota request)
- **Maximum size of a single object:** 5 TB
- **Minimum size of a single object:** 0 bytes (yes, an empty file)
- **Recommended threshold for multipart upload:** Objects larger than 100 MB
- **Required multipart upload:** Objects larger than 5 GB (single PUT is limited to 5 GB)

Amazon has never announced hitting a storage ceiling. Companies store petabytes and even exabytes in S3. Netflix, Airbnb, and the US government all store massive amounts of data in S3.

## Versioning in S3

### What Is Versioning?

By default, when you upload a file to S3 with the same name as an existing file, S3 **overwrites** the old file. It's gone. No way to recover it.

**S3 Versioning** changes this behavior. When enabled, every time you upload an object — even if it has the same key (name) — S3 keeps **all previous versions** instead of replacing them. Each version gets a unique Version ID.

```
Upload report.pdf     → Version ID: abc123 (current)
Upload report.pdf     → Version ID: def456 (current), abc123 (previous)
Upload report.pdf     → Version ID: ghi789 (current), def456, abc123 (all stored)
```

### Why Use Versioning?

- **Accidental overwrites:** You uploaded the wrong version of a file. Restore the previous version in one click.
- **Accidental deletions:** When you delete a file with versioning enabled, S3 doesn't actually delete it — it adds a "Delete Marker." You can remove the delete marker to restore the file.
- **Audit trail:** See the history of changes to a document over time.
- **Compliance:** Some regulations require retaining all versions of records.

### How It's Different From Git

Git is a full version control system designed for code — it tracks what changed, who changed it, shows diffs, supports branching, merging, etc.

S3 versioning just stores full copies of every version. It doesn't track what changed between versions, there's no diff, no branching, no merging. It's simply "keep a copy of every version uploaded."

So while S3 versioning provides a basic form of history and recovery — hence "can be used as version control" — it's not a proper version control system. For code, you always use Git. For non-code files (documents, images, data files) where you just need recovery and history, S3 versioning works fine.

### Versioning + Cost

Every version is stored separately and billed separately. If you have a 1GB file with 10 versions, you're storing 10GB. This can get expensive quickly for large files. Use **Lifecycle Rules** to automatically delete old versions after a set number of days.

### MFA Delete

You can require **MFA (Multi-Factor Authentication)** to permanently delete a versioned object or disable versioning on the bucket. This protects against accidental or malicious permanent deletion — even if an attacker compromises AWS credentials, they can't permanently delete files without also having the MFA device.

## Static Website Hosting on S3

### What Is a Static Website?

A **static website** is one made of only HTML, CSS, and JavaScript files. There is no server-side processing — no PHP, no Node.js running on a server, no database queries per request. Everything runs in the user's browser.

Examples: Portfolio websites, documentation sites, React/Angular SPAs (the build output), landing pages.

S3 can host these directly — no EC2, no web server like Nginx needed.

### How to Host a Static Website on S3

**Step 1: Create an S3 Bucket**
- Name it the same as your domain if you plan to use a custom domain (e.g., `www.myportfolio.com`)
- Choose your region

**Step 2: Upload Your Website Files**
- Upload `index.html`, CSS files, JS files, images, etc.

**Step 3: Disable "Block Public Access"**
By default, S3 blocks all public access — a safety feature so you don't accidentally expose sensitive data. For a public website, you need to turn this off.
- Bucket → Permissions → Block Public Access → Edit → Uncheck all → Save

**Step 4: Enable Static Website Hosting**
- Bucket → Properties → Static website hosting → Enable
- Index document: `index.html`
- Error document: `error.html` (optional — shown when a 404 occurs)
- S3 gives you a website endpoint URL like:
  `http://my-bucket.s3-website.ap-south-1.amazonaws.com`

**Step 5: Add a Bucket Policy for Public Read Access**
Even after disabling Block Public Access, individual objects aren't public yet. You need a bucket policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket-name/*"
    }
  ]
}
```

- `Principal: "*"` means anyone in the world
- `Action: "s3:GetObject"` means read access only — nobody can upload, delete, or list
- `Resource: "arn:aws:s3:::my-bucket-name/*"` means all objects inside the bucket

**Step 6: Access Your Website**
Open the S3 website URL in a browser. Your site loads — served by S3, no server.

**To use a custom domain (myportfolio.com):**
- Create a Route53 ALIAS record pointing `myportfolio.com` → S3 website endpoint
- For HTTPS on a custom domain, put CloudFront in front of S3 (S3 website hosting only supports HTTP, not HTTPS directly)

## S3 Key Properties — In Detail

### Cost Effectiveness

S3 is priced in three dimensions:

**1. Storage cost (per GB per month):**
Different storage classes have different prices. As of current AWS pricing (in USD):

| Storage Class | Price | Access Pattern |
|---|---|---|
| Standard | ~$0.023/GB/month | Frequently accessed |
| Standard-IA | ~$0.0125/GB/month | Infrequent access, retrieval fee applies |
| One Zone-IA | ~$0.01/GB/month | Infrequent, okay to lose if AZ fails |
| Intelligent-Tiering | ~$0.023/GB + monitoring fee | Unknown/changing access patterns |
| Glacier Instant Retrieval | ~$0.004/GB/month | Archive, millisecond retrieval |
| Glacier Flexible Retrieval | ~$0.0036/GB/month | Archive, minutes-to-hours retrieval |
| Glacier Deep Archive | ~$0.00099/GB/month | Coldest archive, 12-hour retrieval |

For comparison: 1TB of data costs about $23/month in Standard, or less than $1/month in Glacier Deep Archive.

**2. Request costs:** A small fee per request (GET, PUT, LIST, etc.). Very cheap per request but adds up at massive scale.

**3. Data transfer:** Uploading to S3 is free. Downloading from S3 to the internet has a cost. Transfer within the same region to other AWS services is free or very cheap.

**Lifecycle Rules for cost optimization:**
You can automatically transition objects to cheaper storage classes as they age. Example: keep last 30 days in Standard, move to Standard-IA after 30 days, move to Glacier after 90 days, delete after 365 days. Fully automated — no manual work.

### Availability

S3 Standard offers **99.99% availability** — about 52 minutes of potential downtime per year, though in practice S3 outages are extremely rare.

Different storage classes have different availability SLAs:
- Standard: 99.99%
- Standard-IA: 99.9%
- One Zone-IA: 99.5% (because it's only in one AZ)
- Glacier classes: 99.99%

AWS achieves availability through geographic redundancy (multiple AZs), automatic failover, and a global infrastructure with massive redundancy at every layer — power, networking, cooling, hardware.

---

### Performance

**High throughput:** S3 supports **3,500 PUT/COPY/POST/DELETE requests per second per prefix** and **5,500 GET/HEAD requests per second per prefix**.

A "prefix" is basically a folder path. If you spread objects across multiple prefixes (e.g., `users/`, `products/`, `logs/`), you multiply the throughput. At scale, you can achieve millions of requests per second.

**Multipart Upload:**
For large files (>100MB), S3 supports multipart upload — the file is split into chunks and uploaded in parallel. Benefits:
- Faster uploads (parallel)
- If one part fails, only that part needs to be re-uploaded
- Can pause and resume uploads

**Transfer Acceleration:**
For users uploading to S3 from far away, **S3 Transfer Acceleration** uses AWS's CloudFront edge locations. Instead of uploading directly to S3 in Mumbai, a user in the US uploads to the nearest AWS edge location (in the US), and AWS's backbone network transfers it to Mumbai. This can be significantly faster for large files across continents.

---

### Security

S3 has multiple layers of security:

**1. Block Public Access (Bucket-level safety)**
AWS has a master "Block Public Access" setting at both the account level and bucket level. Even if you add a policy that makes something public, this setting overrides it. Enable it by default on all buckets that aren't meant to be public. This has prevented countless data leaks.

**2. Bucket Policies (Resource-based policies — explained below)**
JSON policies attached to the bucket itself defining who can access what.

**3. IAM Policies (Identity-based policies)**
Control what IAM users and roles can do with S3 buckets.

**4. Encryption at Rest**
S3 can automatically encrypt all stored objects:
- **SSE-S3 (Server-Side Encryption with S3 keys):** AWS manages the encryption keys. Default. Transparent.
- **SSE-KMS (Server-Side Encryption with KMS keys):** You use AWS Key Management Service to manage keys. Gives you control, audit logs, and key rotation.
- **SSE-C (Customer-provided keys):** You provide the encryption key with every request. AWS uses it to encrypt/decrypt but never stores it.
- **Client-side encryption:** You encrypt before uploading. AWS never sees the unencrypted data.

**5. Encryption in Transit**
All S3 communication uses HTTPS/TLS by default. You can enforce this with a bucket policy condition.

**6. S3 Access Logs**
Enable access logging to capture every request made to your bucket — who accessed it, when, from what IP, what they did. Stored in another S3 bucket.

**7. AWS CloudTrail**
Tracks all S3 API calls (bucket creation, policy changes, object deletions) with full audit trail including who did it and when.

---

### Scalability

S3 is designed to scale infinitely without any configuration on your part.

- Add 1 file or 1 billion files — same performance, same reliability, no changes needed
- S3 automatically scales to handle any number of requests
- No capacity planning required
- No scaling events or scaling policies
- New objects are immediately accessible — no propagation delay

This is fundamentally different from EC2 where you have to plan for scale (ASG, instance types, etc.). With S3, you just use it.

## Bucket Policies — In Detail

### What Is a Bucket Policy?

A Bucket Policy is a **JSON document attached directly to an S3 bucket** that defines who can access the bucket and what they can do. It's a **resource-based policy** — meaning it's on the resource (bucket), not on the identity (user/role).

This is different from IAM policies (which are attached to users, groups, and roles). Bucket policies can grant access to:
- Other AWS accounts entirely
- Specific IAM users or roles
- Everyone on the internet (`*`)
- Specific IP addresses or VPCs

### Structure of a Bucket Policy

Every bucket policy has this structure:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "optional-statement-id",
      "Effect": "Allow",      ← or "Deny"
      "Principal": "...",     ← WHO this applies to
      "Action": "...",        ← WHAT they can do
      "Resource": "...",      ← WHICH resource
      "Condition": { ... }    ← optional WHEN/IF conditions
    }
  ]
}
```

**Version:** Always `"2012-10-17"` — this is the policy language version. Don't change it.

**Sid:** Statement ID — just a label for the statement. Optional but good for readability.

**Effect:** `"Allow"` or `"Deny"`. Deny always overrides Allow.

**Principal:** WHO the policy applies to.
- `"*"` → everyone (anonymous public access)
- `"AWS": "arn:aws:iam::123456789:root"` → specific AWS account
- `"AWS": "arn:aws:iam::123456789:user/john"` → specific IAM user
- `"AWS": "arn:aws:iam::123456789:role/MyEC2Role"` → specific IAM role
- `"Service": "cloudtrail.amazonaws.com"` → AWS service

**Action:** WHAT they can do.
Common S3 actions:

| Action | What It Allows |
|---|---|
| `s3:GetObject` | Download/read objects |
| `s3:PutObject` | Upload/write objects |
| `s3:DeleteObject` | Delete objects |
| `s3:ListBucket` | List objects in the bucket |
| `s3:GetBucketPolicy` | Read the bucket policy |
| `s3:PutBucketPolicy` | Change the bucket policy |
| `s3:*` | All S3 actions |

**Resource:** WHICH resource the policy applies to.
- `"arn:aws:s3:::my-bucket"` → the bucket itself (for actions like ListBucket)
- `"arn:aws:s3:::my-bucket/*"` → all objects inside the bucket
- Both are often needed together

**Condition:** Optional fine-grained conditions.

---

### Important Bucket Policy Examples

**1. Make all objects publicly readable (static website)**
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-bucket/*"
  }]
}
```

**2. Allow a specific EC2 role to read from the bucket**
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::123456789012:role/MyEC2Role"
    },
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": [
      "arn:aws:s3:::my-bucket",
      "arn:aws:s3:::my-bucket/*"
    ]
  }]
}
```

**3. Deny all non-HTTPS requests (enforce encryption in transit)**
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": [
      "arn:aws:s3:::my-bucket",
      "arn:aws:s3:::my-bucket/*"
    ],
    "Condition": {
      "Bool": {
        "aws:SecureTransport": "false"
      }
    }
  }]
}
```
This denies any request not using HTTPS. `aws:SecureTransport: false` = the request is NOT using HTTPS.

**4. Allow access only from a specific IP address**
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": "arn:aws:s3:::my-bucket/*",
    "Condition": {
      "NotIpAddress": {
        "aws:SourceIp": "203.0.113.0/24"
      }
    }
  }]
}
```
Denies all requests NOT coming from the IP range `203.0.113.0/24`. Only that IP range can access the bucket.

**5. Allow access only from within a specific VPC**
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": "arn:aws:s3:::my-bucket/*",
    "Condition": {
      "StringNotEquals": {
        "aws:SourceVpc": "vpc-0abc123def456"
      }
    }
  }]
}
```
Denies access from anywhere except your specific VPC. Combined with a VPC Endpoint, this means ONLY your internal EC2 instances can access this bucket — even if someone has the URL, they can't access it from outside the VPC.

**6. Cross-account access — Allow another AWS account to upload**
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::987654321098:root"
    },
    "Action": "s3:PutObject",
    "Resource": "arn:aws:s3:::my-bucket/*"
  }]
}
```
Grants the other AWS account permission to upload objects to your bucket.

---

### IAM Policy vs Bucket Policy — When to Use Which?

| Scenario | Use |
|---|---|
| Grant an IAM user in the SAME account S3 access | IAM Policy |
| Make a bucket publicly accessible | Bucket Policy |
| Grant access to a different AWS account | Bucket Policy |
| Allow an AWS service (like CloudTrail) to write to S3 | Bucket Policy |
| Restrict access based on IP address | Bucket Policy Condition |
| Restrict access to HTTPS only | Bucket Policy Condition |
| Give an EC2 role access to S3 | Either (IAM Policy on Role is cleaner) |

## Other Important S3 Features to Know

### Pre-Signed URLs
You can generate a **temporary URL** for a private object that gives time-limited access to anyone with the URL — without making the object permanently public.

Example: A user pays for a report on your website. Your backend generates a pre-signed URL valid for 15 minutes. The user downloads the report through that URL. After 15 minutes, the URL expires. Nobody else can use it.

```bash
aws s3 presign s3://my-bucket/private-report.pdf --expires-in 900
```
Returns a URL valid for 900 seconds (15 minutes).

### S3 Event Notifications
Trigger an action automatically when something happens in S3 — a file is uploaded, deleted, or replicated. S3 can notify:
- **Lambda function** — run code when a file is uploaded (e.g., resize an image, process a CSV)
- **SQS queue** — queue the event for processing
- **SNS topic** — send a notification/alert

Example: When a user uploads a video to S3, an event notification triggers a Lambda function that converts it to multiple resolutions and saves the outputs back to S3.

### Cross-Region Replication (CRR)
Automatically replicate objects from a bucket in one region to a bucket in a different region. Used for:
- Disaster recovery (keep a copy in another region)
- Compliance (data must exist in specific regions)
- Reducing latency (serve users from the nearest region)
Requires versioning enabled on both source and destination.

### S3 Object Lock
Prevent objects from being deleted or overwritten for a fixed period of time or indefinitely. Used for:
- Compliance (SEC regulations require storing financial records for 7 years, unmodifiable)
- Protection against ransomware (attackers can't encrypt or delete your backups)

Two modes:
- **Governance mode:** Most users can't delete. Privileged users with special permissions can.
- **Compliance mode:** Nobody can delete — not even root. Period. Not AWS support, not anyone.
